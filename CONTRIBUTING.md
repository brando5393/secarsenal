# Contributing

Contributions that improve an OS entry, fix the tools sync script, or
improve the site itself are welcome.

## Tool entries — don't hand-edit these

Everything under `src/content/tools/` is generated by one of seven
scripts and gets overwritten the next time it runs (each skips any
tool already covered by an earlier one, in this order):

1. `scripts/sync-kali-tools.mjs` — from
   [Kali's official tool pages](https://www.kali.org/tools/all-tools/).
2. `scripts/sync-blackarch-tools.mjs` — from
   [BlackArch's official tool table](https://blackarch.org/tools.html).
3. `scripts/sync-remnux-tools.mjs` — from
   [REMnux's "Discover the Tools" docs](https://docs.remnux.org/discover-the-tools/analyze+documents).
4. `scripts/sync-tails-tools.mjs` — from
   [Tails' official included-software page](https://tails.net/doc/about/features/index.en.html).
5. `scripts/sync-security-onion-tools.mjs` — from
   [Security Onion's official tools docs](https://docs.securityonion.net/en/2.4/tools.html).
6. `scripts/sync-archstrike-tools.mjs` — from
   [ArchStrike's official package table](https://archstrike.org/packages).
7. `scripts/sync-flare-vm-tools.mjs` — from
   [FLARE VM's own package list](https://github.com/mandiant/flare-vm/blob/main/config.xml).
8. `scripts/sync-tpot-tools.mjs` — from
   [T-Pot's own "Honeypots and Tools" README section](https://github.com/telekom-security/tpotce#honeypots-and-tools).

If a tool entry is wrong:

- **Wrong upstream too?** Fix it there (Kali's tool pages have an "Edit
  this page" link; for BlackArch, REMnux, or Tails, open an issue/PR
  against their respective repos) — this project mirrors their data.
- **Wrong only here (a parsing bug)?** Fix the extraction logic in the
  relevant sync script, run the matching `npm run sync-tools*` command
  to regenerate, and include the regenerated files in your PR.

Adding another source: write a new `scripts/sync-<name>-tools.mjs` that
reads the existing manifests (`scripts/manifests/*.json`) to skip
already-covered tools, and writes its own `scripts/manifests/<name>.json`
so its files can be tracked and safely pruned independently — see
`scripts/sync-utils.mjs` for the shared helpers (manifest read/write,
`pruneStale`, `mapWithConcurrency`, `isUrlReachable`). Check first that
the OS actually publishes something scrapable — Parrot Security OS was
evaluated and doesn't (its docs page explicitly points to upstream
`man` pages instead of maintaining a list).

## Adding or updating an OS entry

There's no single official index of "all pentest operating systems"
the way Kali indexes its own tools, so this collection stays
hand-curated — though `scripts/discover-os.mjs` (see
`.github/workflows/discover-os.yml`) surfaces new candidates monthly
from [Rawsec's CyberSecurity Inventory](https://github.com/noraj/rawsec-cybersecurity-inventory)
as a draft PR. If you're processing one of those PRs, follow the
`review-os-candidates` skill (`.claude/skills/review-os-candidates/`)
rather than merging the drafts as-is — it covers deciding sync script
vs. manual entry, verifying maintenance status independently of
Rawsec's own classification, and known pitfalls from past runs.

1. Add or edit a Markdown file under `src/content/os/`. Match the
   schema in `src/content.config.ts` — `npm run dev` / `npm run build`
   will fail with a clear error if a field is missing or the wrong
   type.
2. Set `lastVerified` to the date you personally confirmed the
   description and links below are accurate.
3. Link only to official sources: the project's own documentation,
   official download page, and/or its canonical source repository.
4. Run `npm run check-links` locally before opening a PR to confirm
   your new links resolve.
5. Keep descriptions factual and neutral — what the OS is, what
   category it belongs to, and how to get started with it from the
   official source. No exploit code, no step-by-step attack
   walkthroughs against real/example targets.

## Content scope

This project is a reference catalog, not a tutorial site. "Getting
started" sections should point readers to the *official* documentation
for depth, not attempt to replace it here.

## Reporting issues

Use GitHub Issues for broken links, stale entries, sync-script parsing
bugs, or factual corrections. See `SECURITY.md` for how to report a
security vulnerability instead of a content issue.
